# 🚀 Getting start with Next.js

Rename the file `.env.example.local` to `.env.local` and fill the variables with your own credentials.

## 💻 Development local

Next.js will use Strapi and our API to fetch pages and data.  
You have two options to run the project locally:

### Run Strapi and API locally

You have to run Strapi and our API locally (refer to repositories README.md).  
After that, you can run the project with:

```bash
npm run dev
```

<!-- prettier-ignore -->
> 💡 Note : Next.js will use DEV_* variables from `.env.local` file.

> 🚨 **Since version 18 - lts/hydrogen,
> Node do NOT use anymore `undici` as HTTP/1.1 client but has his proper global fetch API.**
> `localhost` is not recognized by Node fetch API (it tries to resolve `localhost`to ipv6 instead of ipv4).
> Replace it by `127.0.0.1` in your `.env.local` file to explicitly use ipv4 and deal with this issue.

### Use our staging (integration) environment

Run the following command:

```bash
npm run int
```

<!-- prettier-ignore -->
> 💡 Note : Next.js will use INT_* variables from `.env.local` file.

### SSL and HTTPS

Some features need SSL to worked properly (HTTPS). It is the case
for `Web Share` [API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Share_API).

Two solutions are available:

- Use a self-signed certificate, and
  a [custom Next.js server](https://nextjs.org/docs/advanced-features/custom-server) (more secure but more complex to
  set up)
- Use a reverse proxy as [local-ssl-proxy](https://www.npmjs.com/package/local-ssl-proxy) (less secure but easier to set
  up)

We advise you to use the second solution.

```bash
➜  ~ npx local-ssl-proxy --source 443 --target 3000
Started proxy: https://localhost:443 → http://localhost:3000
```

`443` target port is the default port for HTTPS but you can change it.  
`3000` is the port used by Next.js by default, but be free to change it if necessary.

> **🚨DISCLAIMER: This is not a secure solution and should only be used for development purposes only !**

For production, HTTPS is handled by Google Cloud Platform.

Bitbucket's pipelines are used to deploy the Next.js project on GCP Cloud Run.

🗒️ Please check if Bitbucket service account has the following roles :

- Cloud Build Service Account (Compte de service Cloud Build)
- Cloud Run Developer (Développeur Cloud Run)
- Service Account User (Utilisateur de compte de service)

> 💡 You may need to activate the service account with GCLoud
> CLI : https://cloud.google.com/sdk/gcloud/reference/auth/activate-service-account

```bash
gcloud auth activate-service-account <service@account>.iam.gserviceaccount.com --key-file <key_file>.json
```

## ⚙️ Scripts

We provide scripts to automate the manual steps of the deployment process.  
Bitbucket pipelines will not use these scripts !

> 💡 To execute the following scripts, you have to be authenticated with GCloud CLI and have the right permissions.

```bash
# Build Docker image
sh scripts/docker.build.sh --<environment-flag>

# Push Docker image to Google Container Registry
sh scripts/docker.push.sh --<environment-flag>

# Deploy Docker image to Google Cloud Run
sh scripts/docker.deploy.sh --<environment-flag>

# Run all scripts
sh scripts/deploy.sh --<environment-flag>
```

> 💡 `<environment-flag>`: `integration` or `production`

> ⚠️ In some cases, you may encounter `Permission denied` error. You have to improve the permissions for all scripts.

```bash
# Path: $ appines_landing
sudo chmod -R +x scripts
```

# 🚧 Application Architecture

## ✍️ Naming conventions

For consistency, we use the following naming conventions:

- `PascalCase` for React components :
    - ❌ `myComponent`
    - ✅ `MyComponent`
- `camelCase` for variables, functions and TypeScript/Javascript files :
    - ❌`let my_variable`
    - ✅ `let myVariable`
- `kebab-case` for CSS modules, folders and other files* :
    - ❌ `myModule.module.css`, `src/lib/fetchApi/index.ts`, `publicView.d.ts`
    - ✅ `my-module.module.css`, `src/lib/fetch-api/index.ts`, `public-view.d.ts`

> 💡 *Use of CSS modules is deprecated. Prefer TailwindCSS inside className attribute.

## 📁 File structure

```bash
├── components
├── config
├── constants
├── containers
├── env
├── lib
├── pages
├── public
├── scripts
├── styles
└── types
```

`/components` : React components (UI, layout, carousel, etc.)  
`/config` : Environment variables  
`/constants` : Constants (colors, breakpoints, etc.)  
`/containers` : React components (pages, sections, etc.)  
`/env` : Environment variables  
`/lib` : Librairies (analytics, api, etc.)  
`/pages` : Next.js pages  
`/public` : Static files (images, fonts, etc.)  
`/scripts` : Scripts to automate the deployment process  
`/styles` : CSS and Tailwind styles  
`/types` : Typescript types

#### 🗂️ Config folder

We use different environment variables for each environment : `development`, `integration` and `production`.
Thanks to the `@/config/index.ts` file, we can easily switch between environments by changing the `APP_ENV` variable.

```typescript
if (process.env.APP_ENV === "production") env = "production";
if (process.env.APP_ENV === "integration") env = "integration";
if (process.env.APP_ENV === "development") env = "development";
```

> ⚠️ It's important to understand that the `APP_ENV` variable is used to switch between environments when we run the
> application locally.
> Otherwise, the `NODE_ENV` variable is used to switch between `development` and `production` mode.

From Next.js point of view, there is no difference between `integration` and `production` mode.
On `Cloud Run` environment, `NODE_ENV` is set to `production` but it's important to use `integration` or `production`
credentials in function of the environment we want to deploy.
In fact, credentials are already set in Bitbucket deployment variables.

#### 🗂️ Env folder

This folder is used to store environment variables for Docker build process when we deploy the application on Google
Cloud Platform (GCP)
from local environment. In most cases, this folder keeps empty.

#### 🗂️ Pages folder

```bash
@/src/pages
├── [[...path]]
├── 404
├── 410
├── _error
├── annonces
├── api
├── etablissements
├── formations
├── login
├── reset-password
├── signup-confirmed
```

- `[[...path]]`: This directory is used to generate pages from Strapi data.
- `404`: This directory contains the page that is displayed when a user navigates to a non-existent route.
- `410`: This directory contains the page that is displayed when a user navigates to a route that has been removed.
- `_error`: This directory contains the page that is displayed when an error occurs on the server (other than a 404 or
  410).
- `annonces`: This directory contains the search engine page and public views for job offers.
- `api`: This directory contains the API endpoints for the application.
- `etablissements`: This directory contains the search engine page and public views for establishments (offices).
- `formations`: This directory contains the search engine page and public views for courses.
- `login`: This directory contains the page and functionality for logging in.
- `reset-password`: This directory contains the page and functionality for resetting a user's password.
- `signup-confirmed`: This directory contains the page for confirming user's subscription.

To generate a landing page, Next.js fetch data from Strapi thanks to `setStaticProps` helper.
We use 'path' parameter to fetch the right page.

> 💡 `path` parameter can be :
>
> - `undefined` if the user navigates to the root of the website (i.e. `/` path)
> - `string` if the user navigates to a specific page (i.e. `/about-us` path)
> - `string[]` if the user navigates to a specific page with a specific locale (i.e. `/fr/about-us` path)
>
> If you're not familiar with this concept, please check the following
> link : https://nextjs.org/docs/routing/dynamic-routes#optional-catch-all-routes

```typescript
// Fetch props from Strapi
let data = await getPropsForSpecificPath(path, context.locale, context.preview);
```

`getPropsForSpecificPath` returns the page data from Strapi with this main attributes `ContentBlocks`,
corresponding to the page 'container' (Herozone, LastArticles, etc.)

If `getPropsForSpecificPath` returns `null` or `undefined`, the page will be rendered with a 404 error.

# 📊 Analytics and cookies management

Third-party cookies are used to collect data about the use of the site. To be conform with the GDPR,
we use a cookie banner to ask the user to accept or refuse the cookies.

Cookie banner is handled by `Axeptio` service.

All analytics scripts are located in `containers/_metadata/AnalyticsScripts.tsx` file :

- Mixpanel
- Google Analytics
- Google Ads
- Facebook Pixel
- Bing

## Load scripts and disable cookies by default

We load the scripts and disable cookies by default.

```typescript
// Mixpanel
mixpanel.init("${mixpanelToken}", {
  debug: process.env.NODE_ENV === "development" || process.env.APP_ENV === "development",
  host: "api-eu.mixpanel.com", // EU server
  disable_persistence: true,
  disable_cookie: true,
});

// Google Analytics and Google Ads
gtag("consent", "default", {
  ad_storage: "denied",
  analytics_storage: "denied",
});

// 💡 For Facebook Pixel, we load the scripts but we don't initialize it
```

Then, we enable cookies when the user accepts it.
Axeptio allows us to listen to the user's choice thanks to `cookies:complete` event.

```typescript
axeptio.on("cookies:complete", function(choices) {
  /* 👇 Logic to enable cookies 👇 */

  // Mixpanel
  if (choices[mixpanelVendorName]) {
    mixpanel.set_config({
      disable_persistence: false,
      disable_cookie: false,
    });
  }

  // Google Analytics
  if (choices[gaVendorName]) {
    consentSettings.analytics_storage = "granted";
  }

  // Google Ads
  if (choices[adsVendorName]) {
    consentSettings.ad_storage = "granted";
  }

  // Facebook Pixel
  if (choices[fbPixelVendorName]) {
    fbq("init", facebookPixelId);
    fbq("track", "PageView");
  }
});
```

> 💡 `vendorName` is the name of the cookie set in Axeptio admin dashboard for each service.

Thanks to this logic, we can track anonymous events and enable cookies only if the user accepts it.
